# 24 · 生产化与开源化路线图（把插件工厂当成 GitHub 项目运作）

> 目标：把 `dsh-plugin-factory` 从"单人工位可用的插件集合"升级为
> **团队可运维、业务人员可自助使用、可开源迭代的插件平台**。
> 结论：功能基础已经具备（12 插件 / 4 类执行层 / 21 测试 / 写操作治理），
> 缺的是**工程化基线、运行时硬化、插件生命周期、自助流水线、安全与治理**五块。

---

## 一、先定义"开放给团队/业务人员自助使用"

"自助使用"不是一个开关，是 3 级能力。生产开放至少要 L1 + 受控的 L2。

| 级别 | 业务人员能做什么 | 需要平台具备 | 当前 |
|---|---|---|---|
| **L1 自助运行** | 在目录里选插件 → 填参数 → 看进度 → 下载报告；能查历史任务 | 插件目录/参数表单、任务 API + 权限、报告链接、运行审计 | ❌ 目前只能靠 AI 会话调 MCP |
| **L2 自助提需求** | 填业务描述 → 自动生成插件 PR → CI 验证 → 人工审核 → 上线 | 需求模板、生成流水线、CI 门禁、审核/发布流程 | ⚠️ 流程文档有，靠人工复制执行 |
| **L3 自助维护** | 改参数/升级版本/回滚/下线自己负责的插件 | 插件生命周期 CLI、版本与兼容矩阵、负责人制 | ❌ 无 |

**验收定义**：一个不懂代码的业务人员，在浏览器里完成"跑一次插件拿报告"和"提一个新插件需求"，
全程不需要 PowerShell、不需要找开发改文件；出问题 30 分钟内能定位（日志/任务号/审计）。

## 三、目标架构（分层，避免过度设计）

```
┌─────────────────────────────────────────────────────────────┐
│ 接入层：Web Console（L1/L2 自助） / DSH Skill / CLI          │
├─────────────────────────────────────────────────────────────┤
│ 控制面 Gateway（新）：统一鉴权、RBAC、限流、路由、审计、指标   │
│   - 用户/团队/Token/Scope；任务提交与查询代理                 │
│   - 审批流（写操作）；插件目录与健康状态                       │
├─────────────────────────────────────────────────────────────┤
│ 插件运行面（现 shared runtime，本地 127.0.0.1 端口）           │
│   runtime: 任务引擎(SQLite)/鉴权/写四闸/指标/日志/看门狗        │
│   plugins/<id>: service + MCP + SKILL + report + tests       │
├─────────────────────────────────────────────────────────────┤
│ 发布面：Registry（插件目录）+ Release 产物 + 兼容矩阵          │
├─────────────────────────────────────────────────────────────┤
│ 工程面：monorepo + CI/CD + Changesets + 文档站 + 安全扫描      │
└─────────────────────────────────────────────────────────────┘
```

要点：

1. **不要 12 个端口直接对外**。加一个 Gateway（例如 8080），插件服务继续只监听 `127.0.0.1`。
   Gateway 负责登录/Token、按插件与权限路由、统一审计与指标；业务人员只面对一个地址。
2. **单机生产级优先**：团队 ≤10 人时，Gateway + SQLite + NSSM/systemd + 备份即可，不需要 K8s/Postgres。
   何时升级：并发 >50、跨机/跨团队、需要隔离租户时，再拆容器与 Postgres。
3. **插件是"包"不是"目录"**：`plugins/<id>/package.json` + `plugin.json`(schema) + `test/` + `sample/`，
   版本独立、可发布、可回滚。

### 3.1 建议目录结构（monorepo）

```
packages/
  runtime/        @factory/runtime      任务引擎/鉴权/写闸门/指标/日志
  sdk/            @factory/plugin-sdk   definePlugin + manifest schema + 测试工具
  cli/            @factory/cli          new/deploy/doctor/test/smoke/render/release
  report-kit/     @factory/report-kit
  config/         @factory/config       路径/环境/平台适配（DPAPI、服务托管、浏览器会话）
apps/
  gateway/        统一接入与权限
  registry/       插件目录（静态站/JSON index）
  console/        业务人员运行台（L1）
plugins/
  <id>/           plugin.json + src + test + sample + README
templates/plugin/ 新插件脚手架
fixtures/         确定性模拟上游/站点/夹具（复用本次 4 个插件的做法）
docs/             文档站（版本化）
.github/          workflows / issue 模板 / CODEOWNERS / PR 模板
```

### 3.2 关键契约（先定，后面才不会返工）

- `plugin.json` JSON Schema：id/version/type/paramsSchema/outputSchema/permissions/quota/owner/runtimeRange。
- 任务 API 契约：`POST /jobs`、`GET /jobs/:id`、`/result`、`/cancel` 已有，补 **OpenAPI 文档 + 错误码表**。
- dataset 契约：沿用 `docs/10`，加 JSON Schema 校验（报告生成器前置校验）。
- 权限模型：`admin / operator / analyst / viewer` + 插件级 scope（`run:shop-list`、`write:coupon-push`）。
- 版本兼容：插件声明 `runtimeRange`（如 `^3.2`），发布时校验。

## 四、工程化基线（GitHub 开源项目的基本盘）

### 4.1 仓库与构建（P0，2–3 天）

1. `git init`，首次提交前处理：
   - `.gitignore`：`node_modules/`、`**/data/jobs/`、`**/report/*.html`（样例除外）、`platform/secrets/*.enc`、`data/sessions/`、`*.log`、`*.db`、`cordis.patch.yml.bak.*`；
   - 运行数据迁出仓库：`FACTORY_DATA_ROOT`（默认 `%LOCALAPPDATA%/dsh-plugin-factory`）；
   - 大文件（1.5MB dataset、jobs、node_modules）不入库；样例数据放 `fixtures/` 并脱敏。
2. 根 `package.json` + `package-lock.json`（或 pnpm workspace），`engines.node >= 24`；
   `playwright` 等依赖显式声明，`node_modules` 由 `npm ci` 还原。
3. 路径统一：`packages/config` 提供 `resolveRoot()`（基于 `import.meta.url` / 环境变量），
   禁止业务代码出现 `D:/www/...`；Windows 专用能力走 platform adapter（DPAPI/服务/浏览器会话）。
4. CI 第一版：`npm ci` → `node --test` → `doctor`（无服务时可跑静态部分）→ `node --check`。
5. 首次打 tag `v3.2.0`，`CHANGELOG` 记录本次 6 个修复 + 4 个插件。

### 4.2 CI/CD（P1，3–5 天）

- PR 必过（required checks）：
  `lint` / `typecheck` / `unit` / `contract`（manifest schema、路径、patch）/ `test` / `smoke`（mock 夹具，不连真实系统）/ `secret-scan` / `npm audit` / `docs-build`。
- Windows runner 跑运行时相关（DPAPI/junction 适配层用 mock 单测，不必真 DPAPI）；Linux runner 跑静态与纯逻辑。
- `main` 保护：禁止直推、CODEOWNERS 审核、线性历史（squash）。
- 发布：Changesets 管理版本 → tag → 构建插件 tarball + manifest → Release 附件；
  `factory deploy --artifact` 部署到 staging → 验收 → promote 到 prod（GitHub Environments 人工卡点）。
- 回滚：保留最近 N 个产物，`factory rollback <id>` 一条命令回到上一版本。

### 4.3 开源治理文件（P2，开源前 1 天）

`LICENSE`（建议 Apache-2.0）、`CONTRIBUTING.md`、`SECURITY.md`、`CODE_OF_CONDUCT.md`、
`.github/ISSUE_TEMPLATE/*`（`plugin-request.yml` / `bug.yml`）、`PULL_REQUEST_TEMPLATE.md`、`CODEOWNERS`、
`docs/` 文档站（VitePress），README 加架构图/快速开始/插件目录/CI 徽章。
**开源红线**：仓库内不得出现真实凭证、cookie、业务数据、内网地址；提交前跑 secret-scan + 脱敏检查。

## 五、运行时生产硬化（P0–P1）

| 项 | 要做的事 | 验收 |
|---|---|---|
| 进程托管 | NSSM/systemd 注册 12+ 服务；`factory watch` 改为后台服务；开机自启 | 重启机器后 5 分钟内全部 UP；kill 任一服务 30 秒内自动恢复 |
| 任务看门狗 | runtime 增加 `jobTimeoutMs`（默认关闭，按插件配置）；超时标记 failed 并杀 runner 上下文 | 卡死任务 10 分钟内落 failed，队列继续 |
| 优雅退出 | 停止接收新任务 → 等待运行中任务或超时 → 关闭 SQLite | `down` 不再有半写文件；重启恢复计数为 0 |
| 队列治理 | 队列深度/运行时长指标；单任务最大时长；每用户并发限制 | 队列积压告警；恶意/失控任务不影响他人 |
| 资源上限 | 磁盘/日志配额、任务目录保留策略、日志轮转校验 | 磁盘水位告警；7/30 天策略可配 |
| 幂等与重试 | 已有 `idempotency_key`；补失败重试策略（哪些错误可重试） | 重复提交不重复写；可重试错误自动重试 1 次 |
| 浏览器会话 | storageState 用 DPAPI 加密；过期检测与人工扫码流程 | 磁盘上无明文 cookie；过期错误可读 |
| 依赖与供应链 | 锁文件、`npm audit`、Dependabot/Renovate、Node 版本钉住（`node:sqlite` 仍 experimental） | 高危依赖 0；升级有 CI 回归 |

## 六、插件生命周期与 SDK（P1，核心生产力）

目标：**"装一个插件"从 20 分钟手工操作变成一条命令**，并且可回滚。

```
factory new <id>            # 从模板生成 plugin.json/service/mcp/skill/test/sample/README
factory doctor <id>         # schema + 路径 + 端口 + patch + token + 报告
factory smoke <id>          # 本地 mock 夹具跑端到端（不连真实系统）
factory deploy <id>         # 部署 MCP/SKILL（junction/复制）+ render（加锁）+ 启动 + 健康检查
factory release <id>        # 打包产物 + 版本 + 兼容校验
factory rollback <id>       # 回滚上一版本
factory uninstall <id>      # 停服务 + 摘 patch/registry + 归档数据（不删审计）
```

配套：

- `@factory/plugin-sdk`：`definePlugin({ paramsSchema, outputSchema, runJob })`；
  自动生成参数校验、错误码、mock 夹具接口、测试骨架。
- manifest `plugin.json` 由 SDK 校验；`render` 改为**加锁 + 原子写**，多人/CI 并发安全。
- 插件模板 + 生成提示词（20/21/22）版本化，模板与 SDK 同版本发布。
- 兼容矩阵：runtime ↔ plugin version，发布时静态校验。

## 七、自助流水线（L2，团队/业务人员真正自助）

```
业务人员填 Issue（业务描述模板）
   → 打标 plugin-request
   → AI 生成 Bot：factory new → 填执行层/报告/SKILL/测试 → 开 PR
   → CI 门禁（schema/lint/contract/test/smoke/secret-scan/docs）
   → CODEOWNERS 审核（业务 + 平台）
   → 合并 → 自动 release → 部署 staging
   → 业务验收（报告样例）→ promote prod
   → registry/console 自动出现新插件
```

关键设计：

1. **生成器也是代码**：提示词/模板/SDK 版本化；生成结果必须过 CI，AI 不是"绕过审核的捷径"。
2. **staging 与 prod 分离**：staging 用独立端口段与独立数据根，验收通过才 promote。
3. **插件质量门禁**（certification）：8 节报告、空数据守卫、参数校验、错误可读、契约测试、SKILL 完整、无明文凭证。
4. **负责人制**：`plugin.json.owner`（人/团队），告警与升级通知到 owner。
5. **Console L1**：插件卡片（用途/参数/样例报告/健康/负责人）→ 表单提交 → 任务列表 → 报告下载；
   写插件额外走"申请-审批"（审批人看到计划条数/目标/额度）。

## 八、安全与权限模型（P1）

- **入口统一**：Gateway 校验登录态与 scope；插件服务只信任 Gateway（或校验内部签名 token）。
- **身份贯穿审计**：任务记录 `requester / approver / team / ip / plugin / params hash`；
  写操作审计与任务审计可对账；日志不落明文凭证。
- **Token 治理**：用户 token 可撤销/轮换；service token 由 Gateway 下发、定期轮换；
  不再明文写 patch（MCP 通过启动器注入或从受保护配置读取）。
- **写操作审批**：`request → approve → 短期单次 approval_token`；`confirm_write` 之外再校验审批人；
  额度按用户/团队统计，不只按服务。
- **文件与路径**：MCP `read_result_file` 加白名单（仅任务目录 + 报告目录）；
  `/metrics`、`/internal/stats` 鉴权或仅内网。
- **数据保护**：浏览器会话加密；备份加密；报告与数据访问按权限；PII 脱敏规则。
- **供应链**：锁文件 + 审计 + 签名产物；MCP 依赖集中管理，禁止各插件各自装一套。

## 九、可观测性与运维（P1–P2）

- **日志**：结构化 JSON 已有；补 `traceId/jobId/pluginId/caller`；集中采集（Loki/ELK 或至少按日归档）。
- **指标**：Prometheus 格式（任务数/失败率/队列/时长 p50/p95/写额度/磁盘/浏览器实例/内存）；
  `/metrics` 走 Gateway 鉴权；Grafana 看板。
- **告警**：服务 DOWN、失败率 >5%（5 分钟）、队列 >N、磁盘 >80%、证书/token 临近过期、备份失败；
  通知到 owner（Webhook/企业微信/邮件）。
- **SLO**：可用性 99%（工作时间）、任务 p95 < 2 分钟（API 类）、报告生成成功率 >99%、恢复 RTO 30 分钟/RPO 24 小时。
- **备份**：每日 `jobs.db`（VACUUM INTO）+ 数据目录增量 + secrets + manifests + deployment；
  每月恢复演练；保留 30 天；备份加密。
- **发布**：staging→prod、变更窗口、回滚演练、发布说明（CHANGELOG）。
- **故障演练**：每季度做一次"杀服务/断网/磁盘满/凭证过期"演练。

## 十、路线图（按周）

| 阶段 | 时间 | 内容 | 退出标准 |
|---|---|---|---|
| **P0 工程化基线** | 2–3 天 | git/.gitignore/package+lock/路径 config/数据分离/LICENSE/CI 骨架/docs 同步/首次 tag | 干净克隆 `npm ci && npm test` 全绿；仓库无凭证/数据；`git log` 有基线 |
| **P0 安全收口** | 1–2 天 | Gateway 或端点鉴权收口、storageState 加密、read_result_file 白名单、token 不明文 | 扫描无明文凭证；未授权端点 401；会话文件加密 |
| **P0 运维硬化** | 2–3 天 | NSSM 自启/守护、备份+恢复、告警、任务看门狗 | 重启机器全恢复；kill 自愈；恢复演练 <30min |
| **P1 插件生命周期** | 1 周 | SDK + 模板 + new/deploy/rollback + render 加锁 | 新插件从模板到 smoke 全绿 ≤10 分钟；回滚可用 |
| **P1 CI/CD + 发布** | 1 周 | PR 门禁、Changesets、staging/prod、制品 | PR 无绿灯不可合并；一条命令发布/回滚 |
| **P2 自助 L1** | 1–2 周 | Console + 目录 + 表单 + 任务/报告 + 权限 | 业务人员不看命令行跑通一次盘点 |
| **P2 自助 L2** | 2–3 周 | Issue 模板 + AI 生成 Bot + PR 流水线 + 审核 | 业务提需求 → 上线中人工只做 1 次审核 |
| **P3 开源发布** | 2–4 周 | 文档站/社区文件/插件认证/公开 registry/发布节奏 | 外部开发者 1 天内按 CONTRIBUTING 提 PR 且 CI 全绿 |

**人力假设**：1 人全职约 8–10 周；2 人并行约 5–6 周。**最小可用生产开放**（L1 + P0 全部）约 **2–3 周**。

## 十一、前 10 个动作（建议本周就做）

1. `git init` + `.gitignore` + 首次基线提交（先别 push 公开）。
2. 根 `package.json` + 锁文件，`npm ci` 可复现；Node 版本写 `.nvmrc`/`engines`。
3. 把 `data/jobs`、`reports`、`platform/secrets/*.enc`、`sessions` 移出或忽略；提供 `fixtures/` 样例。
4. 统一路径解析（`FACTORY_ROOT`/`FACTORY_DATA_ROOT`），去掉业务代码里的 `D:/www/...`。
5. 端点鉴权收口：`/metrics`、`/internal/stats`、MCP 文件读取白名单。
6. storageState 加密（DPAPI）+ token 轮换方案。
7. NSSM/systemd 注册 + 开机自启 + 健康告警（先做 Webhook）。
8. 每日备份脚本 + 恢复演练一次（记录 RTO）。

## 十二、不建议现在做的（避免过度设计）

- 上 Kubernetes / 微服务拆分 / 多租户数据库（团队 ≤10 人不需要）。
- MCP 聚合（会改工具命名，收益低，等插件数量 >20 再说）。
- 自研 Web 框架/账号系统（先用现成 Gateway 或反向代理 + 简单 RBAC）。
- 为了让"开源好看"重写 80% 代码；先做基线，再逐步重构。
- 在仓库里保留真实业务数据/凭证（开源前必须清理，这是红线）。

## 十三、风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| Node `node:sqlite` Experimental | 升级 Node 可能破坏任务引擎 | 钉版本 + 升级前跑回归；抽象 store 层 |
| Windows 绑定（DPAPI/junction/PowerShell） | 开源贡献者无法本地跑 | platform adapter + Linux 单测 mock + 文档说明 |
| 硬编码路径/端口 | 换机器/CI 失败 | 统一 config + 端口分配器 |
| 插件质量参差 | 生产事故 | certification 门禁 + owner + staging |
| AI 生成代码不可靠 | 安全/可靠性事故 | 生成必须过 CI + 人工审核；生成器版本化 |
| 单机单点 | 宕机全停 | 备份 + 自愈 + RTO 演练；规模上来再上多机 |
| 凭证/数据泄漏 | 合规风险 | secret-scan + 数据出仓 + 会话加密 + 最小权限 |
