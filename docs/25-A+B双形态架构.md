# 25 · A+B 双形态：对话内自助 + Web 门户自助（同一控制面，两个前端）

> A = 业务人员在 DeepSeek Harness 对话里，由"工厂 Agent"代工造插件；
> B = 业务人员在 Web 门户里自助选插件/提需求/看报告。
> 结论：**两者不是两套产品，而是"一个控制面 + 两个前端"**。先抽控制面，再做 A，最后做 B；
> 直接同时做两套会重复 60% 工作，并且 A 会变成绕过门禁的捷径。

---

## 一、目标形态（一张图）

```
┌──────────────────────────── 前端层 ────────────────────────────┐
│  A：DSH 工厂 Agent（Skill + factory-control MCP）               │
│  B：Web Console（插件目录 / 运行台 / 需求单 / 审批 / 管理后台）   │
└───────────────────────────────┬───────────────────────────────┘
                                │ 同一组 REST/JSON API（带身份与 scope）
┌───────────────────────────────▼───────────────────────────────┐
│ 控制面 Control Plane（新增，核心资产）                          │
│  身份/团队/RBAC · 需求单 · 生成流水线状态机 · 审批 · 审计        │
│  插件包与版本 · Registry · Staging/Prod · 配额 · 指标           │
└───────────────┬───────────────────────────────┬───────────────┘
                │                               │
┌───────────────▼──────────────┐   ┌────────────▼───────────────┐
│ 生成流水线（AI + 工具）       │   │ 运行面（现有 shared runtime）│
│ 需求卡→勘探→生成→校验→staging │   │ 12+ 插件服务（127.0.0.1）    │
│ 产出 PR/产物 + 测试证据       │   │ 任务引擎/写闸门/报告          │
└──────────────────────────────┘   └────────────────────────────┘
```

A 和 B **共享同一套**：身份、需求单、生成状态机、插件包/版本、Registry、审批、审计、任务 API、指标。
差异只在"交互与呈现"：A 用对话 + MCP 工具，B 用页面 + 表单 + 列表。

## 二、必须先抽出来的 6 个共享核心

| # | 核心 | 职责 | 现在有什么 |
|---|---|---|---|
| 1 | **Control Plane API** | 需求单/插件/版本/部署/任务/审批/审计的 REST 契约 | 无（目前是 CLI + 文件） |
| 2 | **身份与权限** | 用户/团队、DSH token 与 Web 登录、RBAC、插件级 scope | 只有 per-service token |
| 3 | **插件包与 Registry** | `plugin.json`(schema)+版本+owner+兼容矩阵+目录 | manifest 雏形，无版本/owner/包 |
| 4 | **生成流水线** | 需求卡校验→勘探→生成→校验→staging 的状态机与产物 | docs/20 的 12 步，人肉执行 |
| 5 | **审批与发布** | staging 验收、写操作审批、promote/rollback、审计 | 只有 `confirm_write` 布尔 |
| 6 | **运行与观测** | 任务 API、队列、指标、告警、备份 | runtime 已有，缺网关/告警/备份 |

**先做 1/2/3，A 和 B 才都有地基。** 4/5/6 可以并行推进。

## 三、A 形态（DSH 对话内自助）

### 3.1 用户旅程

```
业务人员：我想做一个"缺货预警"插件
工厂 Agent：需求卡（数据源？站点/负责人？规则？输出？凭证是否已配？）→ ≤3 个问题
           → 调 probe（接口/字段/枚举/分页）→ 出勘探结论
           → 生成插件包（service/MCP/SKILL/报告/测试）→ 展示 diff + 样例报告
           → 业务确认口径 → 部署 staging → 跑一次真实任务 → 看报告
           → 确认 → promote prod → 登记 owner
```

### 3.2 技术实现

- **一个技能**：`factory-agent` SKILL（SOP + 门禁 + 话术），不把业务逻辑写进 prompt。
- **一组 MCP 工具**（`factory-control-mcp`，薄壳转发 REST）：
  `create_request / probe / generate / get_diff / deploy_staging / run_job / promote / approve_write / list_plugins / rollback`。
- **状态机在后端**，不在对话里：Agent 只能推进状态，不能跳过"校验/审核/验收"。
- **人工卡点**：
  - 需求卡不完整 → 不允许开工；
  - 勘探失败 → 不允许编造字段；
  - 生成后 → 必须展示 diff + 测试证据；
  - staging 验收 → 业务负责人确认口径；
  - 写操作 → 明确审批人，审批记录进审计。
- **A 的天然优势**：业务人员零学习成本，就用现有 DSH 对话；适合 L2（提需求+生成）。
- **A 的天然风险**：AI 容易"看起来做完了"。所以门禁必须在后端，A 只是触发器。

### 3.3 A 的部署前提

工厂和插件跑在**共享主机**上，DSH 在本机通过 MCP 调控制面：
`DSH → factory-control-mcp（本地 stdio）→ HTTPS/VPN → Control Plane（服务器）`。
**不要让每个业务人员本机各跑一套工厂**（凭证/数据/服务会碎片化，无法统一审计）。

## 四、B 形态（Web 门户自助）

### 4.1 页面（MVP 只要 5 个）

1. **插件目录**：卡片（用途/触发词/参数/样例报告/owner/健康/版本）。
2. **运行台**：选插件→表单（按 paramsSchema 生成）→提交→进度→结果→下载报告；历史任务。
3. **需求单**：填业务描述模板→状态跟踪（待勘探/生成中/待审核/staging/已上线）。
4. **审批中心**：写操作申请、插件上线审核、staging 验收。
5. **管理后台**：用户/团队/权限、额度、服务健康、失败任务、审计检索。

### 4.2 技术实现

- 前端：React/Vue 任一；表单由 `paramsSchema` 自动渲染（避免每个插件写页面）。
- 后端：直接复用 Control Plane API（B 不拥有独立业务逻辑）。
- 登录：内部可先"账号+密码/一次性邀请"，后续接 OIDC/LDAP/企业微信。
- 报告：直接链到 HTML 文件（受权限保护），不重复渲染。
- B 适合 L1（跑插件）+ L2（提需求）+ 审批；比 A 更适合"不装 DSH 的纯业务同事"。

## 五、部署拓扑与身份（A+B 都要的关键决定）

**推荐：单台共享主机（Windows 或 Linux）+ 反向代理 + Web/API 门户；插件服务继续只监听 127.0.0.1。**

- 反向代理（Caddy/Nginx）：TLS、登录、IP 白名单/VPN、审计入口。
- DSH 侧：每用户一个 control-plane token（存 DSH profile 的 MCP env），映射到同一用户。
- B 侧：Web 登录，映射到同一用户。
- 插件服务不对外，只被 Control Plane/Gateway 调用。
- 开发/CI 在本机或 runner；staging 与 prod 用不同数据根与端口段。

> 如果坚持"工厂跑在每个人本机"，A 可以用，但 B 无法统一、审计无法完整、凭证会散落。
> 所以 A+B 的前提是**共享控制面**。

## 六、状态机与数据模型（先定，避免边做边改）

```
需求单 request: draft → submitted → probing → designed → generating
                → validating → staging → awaiting_acceptance → published / rejected
插件 plugin:     id / name / type / owner / team / paramsSchema / outputSchema / permissions
版本 version:    semver / artifact / runtimeRange / changelog / status(draft|staging|prod|deprecated)
部署 deployment: pluginId / version / env(staging|prod) / port / health / deployedAt / by
任务 job:        pluginId / version / requester / paramsHash / status / result / report
审批 approval:   type(write|publish|rollback) / requester / approver / scope / token / expiresAt
审计 audit:      actor / action / object / before/after / ip / at（追加写，不可改）
```

## 七、路线图（A+B 都要）

| 阶段 | 时间（1 人，AI 辅助） | 交付 | 退出标准 |
|---|---|---|---|
| **S0 控制面地基** | 2 周 | Control Plane API + 身份/RBAC + plugin.json schema + Registry + 审计骨架 | A 与 B 都能用同一 API 列出插件/提交任务 |
| **S1 A MVP** | 1–2 周 | factory-agent Skill + factory-control MCP + 生成状态机 + staging + 门禁 | 业务人员只靠对话完成一次"描述→staging→报告"，人工只验收 1 次 |
| **S2 B MVP** | 2–3 周 | 目录/运行台/需求单/审批/管理后台（5 页）+ paramsSchema 表单 | 不装 DSH 的同事可自助跑插件、提需求 |
| **S3 生产硬化** | 2–3 周 | 网关/TLS、写操作审批、备份/告警/看门狗、staging→prod、回滚、CI/CD | 重启自愈、恢复 <30min、PR 必绿、可回滚 |
| **S4 开源/社区** | 视需要 2–4 周 | 文档站、贡献指南、插件认证、公开 registry | 外部开发者可按 CONTRIBUTING 提 PR |

**总工期**：1 人约 **7–10 周**到"A+B 可用"；2 人并行约 **5–6 周**；完全生产+开源约 **12–16 周**。

**顺序很重要**：S0 → S1（先用 A 验证流水线）→ S2（B 主要是 UI，接 API 即可）。
不要 S2 先行，否则 B 会等 API，返工最多。

## 九、反模式（A+B 最容易踩的坑）

1. **两套代码**：A 一套、B 一套 → 必然分叉。必须同一 Control Plane。
2. **A 绕过门禁**：对话里"直接生成并上线" → 审计缺失。门禁在后端，A 只是调用方。
3. **先做 B 的 UI**：API 未定，页面全返工。先 API 后 UI。
4. **把生成逻辑写进 prompt**：不可测试、不可版本化。生成器是代码 + 模板，prompt 只做编排。
5. **每台机器各跑一套工厂**：凭证/数据/服务碎片化，B 无法统一。
6. **AI 直接写生产**：必须 staging + 验收 + promote，写操作另走审批。
7. **用 DSH 本地文件当共享状态**：多用户会冲突；状态在 Control Plane。
8. **忽略凭证/登录态**：这是"自助"真正的堵点，比生成代码难。

---

## 十、我的建议路径

1. **先 S0 控制面地基**（2 周）：API + 身份 + plugin 包 + registry + 审计。
2. **再做 S1 A MVP**（1–2 周）：用对话把"描述→生成→staging→报告"跑通，验证生成器质量。
3. **然后 S2 B MVP**（2–3 周）：B 只是同一 API 的 UI，边际成本低。
4. **S3 硬化**（2–3 周）：网关/TLS、审批、备份、告警、CI/CD、回滚。
5. **S4 开源**：等内容稳定、文档与社区文件齐了再做。

**第一个可交付里程碑**（建议 2 周内）：业务人员在 DSH 里说一句需求 → 工厂 Agent 产出**可在 staging 运行、带测试证据和样例报告**的插件，全程留审计；B 暂时不做 UI，但 API 已就绪。
