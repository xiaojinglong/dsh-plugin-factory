## 二、P0：会导致真实使用失败 / 数据不一致

### P0-1 沙箱写白名单漏了父目录 → 文件类插件必然写失败 ★最严重

`apps/generator/portable.cjs:60-68`

```js
const write = new Set()
if (perms.filesystem?.includes('write')) {
  write.add(dataRoot)
  if (typeof args.output_path === 'string' && path.isAbsolute(args.output_path)) write.add(args.output_path)
  ...
}
```

只把**文件路径本身**加入 `--allow-fs-write`，没有加入它所在的目录。而 `lib/connectors/file.js` 的 `writeText()` 第一句就是
`fs.mkdirSync(path.dirname(file), { recursive: true })` —— 目录不在白名单 → `ERR_ACCESS_DENIED`。

已用最小用例复现：

```text
--allow-fs-write=<T>/sub/y.csv
mkdir sub FAIL Access to this API has been restricted. Use --allow-fs-write to manage permissions.
write sub/y FAIL ENOENT
```

影响：**所有声明 `filesystem:["write"]` 的插件，只要写用户目录就报权限错**；报错文案还是英文内部错误，业务人员看不懂。

建议修复（`portable.cjs` 写入块）：

```js
const write = new Set()
if (perms.filesystem?.includes('write')) {
  write.add(dataRoot)
  for (const v of [args.output_path, args.output_dir, args.input_path]) {
    if (typeof v !== 'string' || !path.isAbsolute(v)) continue
    write.add(v)
    write.add(path.dirname(v))          // ★ 父目录必须放行
  }
}
```

同时 `read` 块（第 62 行）对 args 里**任意**绝对路径字符串无条件开放读权限，与 `permissions.filesystem` 声明无关，建议一并收敛到「声明了 read 才放行」。

### P0-2 `NODE_OPTIONS` 未清理 → 在 IDE / CI 里沙箱启动即崩

`apps/generator/generator.cjs:259-266` 把 `...process.env` 整体传给 `sandbox.spawnSandboxed()`，`sandbox.cjs` 未做任何环境净化。

本机 `NODE_OPTIONS=--require=.../node-language-shim.cjs`（Electron 宿主常见），子进程带 `--permission` 后连 shim 都读不了：

```text
ERR_ACCESS_DENIED permission: 'FileSystemRead'
resource: '\\?\C:\Program Files\WorkBuddy\...\node-language-shim.cjs'
```

影响：13 个失败用例里 4 个（generator / sandbox / pipeline / golden tickets）**全部**由它引起，且真实用户机器只要设了 `NODE_OPTIONS` 就复现。便携沙箱 `lib/sandbox.js` 用的是白名单 env，反而没这个问题 —— 两套沙箱行为不一致。

建议：在 `sandbox.cjs` 里统一净化 `NODE_OPTIONS`、`NODE_REPL_EXTERNAL_MODULE`、`DEBUG`，或捕获该错误给出明确提示「检测到 NODE_OPTIONS 注入，已忽略」。

### P0-3 请求体上限 256KB，与 MCP 允许的 200KB/文件 × 多文件冲突

`apps/control-plane/server.cjs:74` `bodyLimit: 256 * 1024`
`apps/factory-control-mcp/index.cjs:132` 每个文件最多 200KB，且 `files` 数量不限。

实测 3×120KB 的多文件插件：

```text
HTTP 413
{"error":{"code":"FST_ERR_CTP_BODY_TOO_LARGE","message":"Request body is too large"}}
```

两个 150KB 的文件就会踩线，且错误是英文、没有「怎么办」。建议 `bodyLimit` 提到 4MB，并在 MCP 侧对 `files` 总大小做校验（中文报错 + 建议拆文件）。

### P0-4 `install` 步骤从不落库 → 控制面状态永远停在 `accept`

`apps/factory-control-mcp/index.cjs:83-114`：`accept` 之后直接安装，**没有任何代码 POST `step=install`**（全仓库 grep 只有 schema 定义和 UI 枚举）。返回体里的 `state: 'accepted'` 是硬编码字符串。

后果：
- `list_requests(state=installed)` 永远查不到东西；`/metrics` 的 byState 失真；
- `pruneRequests` 默认只清 `failed|installed`，这些单永远不被回收 → `state.db` 只增不减。

建议在安装成功/失败后补写 `install` 步骤（`running` → `succeeded|failed`，evidence 放 zip 路径 + sha256）。

### P0-5 `create_plugin` 自动验收，和自己的门禁规则打架

同文件第 83-85 行：

```js
await call('POST', `/requests/${requestId}/accept`, {
  acceptedBy: 'dsh-agent', note: 'portable-host created via DSH natural language',
});
```

但 `docs/70` 节点 13 与 `SKILL.md` 硬规则都写着「用户验收不通过，不得发布」「验收人必须是真实用户」。现在等于**工厂替用户签了字**，而 `accept_request` 工具（要求真实 `acceptedBy`）反而永远不会被调用。

建议：`create_plugin` 增加 `autoAccept`（默认 `false`），自动验收时 `acceptedBy` 记为 `auto:dsh-agent` 且 note 明示「未经人工验收」，交付话术里不许说「已验收」。

## 四、P2：工程与文档

- **13 三份 SKILL.md 漂移**：`skills/factory-agent/SKILL.md` 是 M2 旧版（102 行，讲需求单状态机），`deployment/` 与 `.dsh/` 是新版（254 行，讲 0–15 节点）。应改为单一源 + 安装时复制。
- **14 版本/文档漂移**：README 写 `v3.4.2`，`package.json` 是 `3.2.0`，交付 tag 是 `v3.6.0`；README「28 个插件」「9 个 MCP 工具」实际是 30 / 13。
- **15 Node 门禁过严**：`install.cjs:44` 与 deps-check 硬拦 `<24`。本机 22.22.2 直接拒绝安装，但功能实测可用（`node:sqlite` 只是 ExperimentalWarning）。13 个失败里的 7 个仅因此项。建议降为 `>=22` 并在文档写清 SQLite 实验性风险。
- **16 契约测试非 hermetic**：`contract.test.mjs:63` 读真实 `~/.dsh/cordis.patch.yml`，断言「测试插件不得出现在默认 patch」。用户一旦 `--with-plugins` 装过，测试**永久失败**（本次失败即此）。建议 patch 用临时 fixture 或按 manifest 派生。
- **17 便携安装绑死 DSH 形态**：`dsh-factory.cjs:35` 硬编码 `DeepSeek Harness/.../dsh.cmd`，`profileComposed` 硬编码 `~/.dsh`。换宿主（WorkBuddy 等）会静默失败。建议 `DSH_CLI` / `DSH_HOME` 探测失败时明确报错。
- **18 业务侧无界面**：业务人员仍要开终端跑 `install.cmd` / `start-factory.cmd`。控制面已有 `/requests` `/metrics`，加一个只读看板（单页 HTML + token）能显著降低门槛，也承接「用户可见进度」的承诺。

1. **P0-1 写白名单 + P0-2 环境净化**（半天，直接解锁文件类插件，属"能不能用"）
