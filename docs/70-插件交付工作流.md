# 70 · 插件交付工作流

> 目标：把“造插件”从一次性代码生成，变成**串行、带门禁、可验收、可回滚**的交付流程。
>
> 强制规则：`factory-agent` 每次造插件必须按节点 0 → 15 顺序推进；未通过当前节点，不得进入下一节点。
>
> **爬虫/浏览器类需求额外强制遵守 [`docs/73-爬虫型插件双交付强制标准.md`](73-爬虫型插件双交付强制标准.md)：必须独立爬虫服务 + 薄 DSH 插件，禁止把 Playwright/浏览器/选择器写进插件。**

## 1. 核心原则

1. **串行推进**：一个节点通过才进入下一个。
2. **用户不写代码**：用户只描述流程、扫码/授权、确认结果。
3. **每节点留证据**：Spec、测试报告、zip、安装状态、试点记录。
4. **高风险不承诺全自动**：验证码/强风控/敏感数据只能辅助或走官方接口。
5. **试点不过不放大**：3 → 10 → 30 → 100 → 再谈 1000。
6. **失败可回退**：不把失败包装成成功。

## 2. 工作流总图

```text
0 需求接收
→ 1 需求澄清
→ 2 可行性判定
→ 3 Spec 契约
→ 4 用户交互设计
→ 5 技术设计
→ 6 代码生成
→ 7 静态校验
→ 8 自动测试
→ 9 沙箱验证
→ 10 打包
→ 11 安装
→ 12 小规模试点
→ 13 用户验收
→ 14 发布/注册/回滚
→ 15 运营迭代
```

## 3. 节点定义

| # | 节点 | 输入 | 输出 | 完成标准 | 负责方 |
|---|---|---|---|---|---|
| 0 | 需求接收 | 用户一句话 | 原始需求 | 能复述用户目标，不曲解 | DSH |
| 1 | 需求澄清 | 原始需求 | 6 要素 | 输入/输出/规则/权限/登录态/边界明确 | DSH + 用户 |
| 2 | 可行性判定 | 6 要素 | 绿/黄/红结论 | 明确能不能做、能不能全自动 | DSH + 用户 |
| 3 | Spec 契约 | 澄清结果 | `spec` | 工具、参数、权限、凭证、验收标准齐全 | DSH |
| 4 | 用户交互设计 | Spec | 用户话术 + SKILL | 用户只说自然语言，不出现函数名/参数/job_id | DSH |
| 5 | 技术设计 | Spec | 连接器/依赖/文件结构 | 明确 file/http/browser/desktop、失败策略 | DSH |
| 6 | 代码生成 | 设计 | `files[]` + tests | 无密钥、无绝对路径、可维护 | DSH |
| 7 | 静态校验 | 生成物 | 校验报告 | 语法/Schema/权限/依赖白名单通过 | 工厂 |
| 8 | 自动测试 | 生成物 | 测试报告 | fixture/契约/边界测试通过 | 工厂 |
| 9 | 沙箱验证 | 测试通过物 | 沙箱报告 | 文件/进程/网络权限符合声明 | 工厂 |
| 10 | 打包 | 通过物 | zip + checksum | 可安装、可追溯 | 工厂 |
| 11 | 安装 | zip | 安装结果 | `composed=true`，工具可加载 | 工厂 |
| 12 | 小规模试点 | 已安装插件 | 试点报告 | 3 → 10 → 30 逐级通过 | 用户 + DSH |
| 13 | 用户验收 | 试点结果 | 验收记录 | 用户全程自然语言完成开始/进度/停止/导出 | 用户 |
| 14 | 发布 | 验收通过 | 版本/注册表 | 版本、说明、回滚、已知限制齐全 | 工厂 |
| 15 | 运营迭代 | 线上使用 | 日志/问题 | 有监控、可诊断、可回滚 | 工厂 + 用户 |

## 4. 关键门禁

### 4.1 节点 2：可行性

必须先判定：

| 等级 | 类型 | 交付方式 |
|---|---|---|
| 绿色 | 文件、Excel、CSV、内部 API | 可自动交付 |
| 黄色 | 外部 API、浏览器登录、桌面 UI | 必须试点 + 人工兜底 |
| 红色 | 验证码、强风控、无授权数据 | 不做全自动承诺；只做辅助或官方接口 |

**红色场景不得承诺 1000 条全自动。**

### 4.2 节点 4：用户交互

用户侧禁止出现：

```text
boss_start(...)
job_id
count=
delay_min_seconds
代码块
```

只允许出现：

```text
开始采集
现在进度
停止
导出
```

内部工具名/参数/job_id 只能存在于 DSH 内部，不得写进给用户的说明。

### 4.3 节点 7/8/9：验证

不能只看“能生成”：

- 语法/契约/权限必须通过
- 测试必须真实执行
- 失败必须返回诊断
- 沙箱权限必须匹配声明

### 4.3.1 节点 8/9 目标一致性校验（强制）

“测试通过”不等于“和目标一致”。每个插件必须增加目标一致性校验。

#### 目标契约

在节点 3 必须写清楚：

```text
目标对象：网页/API/文件/桌面应用
目标地址或入口
用户动作
预期输出字段
成功标志
失败/风控处理
明确不做什么
```

#### 一致性测试

必须提交并执行：

```text
tests/target-conformance.test.mjs
```

至少覆盖：

- 目标入口/URL 正确
- 关键输入/参数正确
- 输出字段与目标契约一致
- 成功标志正确
- 失败/空数据不会假成功
- 用户自然语言路径可完成

爬虫型还必须覆盖：

- 关键词编码正确
- 翻页后的 URL/参数正确
- 商品/数据卡片字段完整
- 缺页如实返回
- 登录态复用
- 验证码/滑块进入等待，不绕过

#### 自我修复循环

```text
1. 对照目标契约跑一致性测试
2. 记录 expected / actual / diff
3. 判断差异属于服务、插件、编码、选择器、分页还是成功判定
4. 先修根因，不改验收标准
5. 重新跑目标一致性测试
6. 最多 3 轮
7. 3 轮仍不一致 → 停止交付，报告差异
```

硬规则：

- **禁止修改测试来让失败变通过**
- **禁止把 fixture 结果当成目标一致**
- **禁止只测 `impl.js` 绕过插件**
- **禁止目标不一致仍发布**
- 目标不一致时必须先回退节点 5/6 修复，再重跑节点 8/9/12

#### 目标一致性证据

交付报告必须包含：

```text
expected：
actual：
diff：
修复轮次：
最终结论：一致 / 不一致
未验证项：
```

### 4.3.2 节点 13 验收语义（强制）

工厂不得替用户签字：

```text
create_plugin 默认 autoAccept:false
→ 只到 staging
→ 用户确认目标/结果
→ finalize_plugin({autoAccept:true}) 才验收并安装
```

只有用户已经明确确认目标，并明确要求直接安装时，才允许：

```text
create_plugin({autoAccept:true})
```

验收人必须是真实用户；开发者的“我觉得可以”不算验收。

### 4.4 节点 12：试点

必须逐级放大：

```text
3 条 → 10 条 → 30 条 → 100 条 → 1000 条
```

每级记录：

- 成功率
- 是否触发验证/风控
- 页面/接口是否异常
- 是否能停止、恢复、导出
- 数据是否完整、可追溯

任一级失败，退回节点 2 或 5，不得继续放大。

### 4.5 节点 13：用户验收

验收人必须是真实用户，不是开发者。

只问：

- 你能用自然语言完成吗？
- 你知道现在在做什么吗？
- 失败时知道怎么办吗？
- 结果能直接用吗？
- 你需要看代码吗？

任何一项“否”，不发布。

## 5. 失败回退规则

| 失败节点 | 回退到 |
|---|---|
| Spec 不清楚 | 节点 1 |
| 测试失败 | 节点 6，最多 3 次 |
| 目标一致性失败 | 节点 5/6，修复后重测；3 轮仍失败则停止 |
| 沙箱失败 | 节点 5 |
| 试点失败 | 节点 2 或 5 |
| 验收失败 | 节点 4 |
| 安装失败 | 节点 10/11 |
| 发布失败 | 回滚上一版本 |

## 6. 交付物清单

每个正式插件必须交付：

- `zip` 的路径 + SHA-256
- 版本号
- `SKILL.md`
- 安装/启动/停止说明
- 安装后位置说明
- 换机器迁移说明（见 [`docs/71-插件包位置与迁移.md`](71-插件包位置与迁移.md)）
- 验收报告
- 已知限制
- 失败处理
- 回滚方式
- 数据/隐私说明（涉及个人信息时）

## 7. 完成定义

不是：

```text
zip 生成了
```

而是：

```text
用户用一句自然语言
→ 插件启动
→ 进度可读
→ 失败可处理
→ 结果可导出
→ 不需要看代码
```

## 8. 用户可见交付看板

交付流程不能只在后台跑。用户必须能看到：

- 现在在哪个节点
- 哪些节点已经通过
- 当前卡在哪里
- 为什么卡住
- 下一步需要用户做什么
- 有什么风险/限制

### 8.1 展示原则

1. 用**业务语言**，不用内部节点编号、工具名、job_id。
2. 只在关键节点更新：开始、通过、失败、等待用户、完成。
3. 每次更新都必须包含：状态、证据、下一步。
4. 不刷屏：不是每一步代码都汇报。
5. 用户能自然语言确认/驳回，不需要看代码。

### 8.2 标准进度卡

```text
【插件交付：BOSS 简历采集】
当前阶段：试点验证（第 12 步）
状态：进行中

已完成：
✓ 需求确认
✓ 可行性判断（黄色：需要人工扫码 + 风控）
✓ Spec 契约
✓ 用户交互设计
✓ 代码生成与自动测试
✓ 安装

正在做：
· 3 条小规模试点

需要你：
· 在 Chrome 中扫码登录
· 保持窗口打开

风险：
· BOSS 推荐页可能重载 iframe
· 若出现验证码会暂停，不绕过

下一步：
· 3 条通过后，再申请 10 条试点
```

### 8.3 用户可见节点名

| 内部节点 | 对用户显示 |
|---|---|
| 0 需求接收 | 需求确认 |
| 1 需求澄清 | 补充信息 |
| 2 可行性判定 | 可行性评估 |
| 3 Spec 契约 | 方案确认 |
| 4 用户交互设计 | 使用方式确认 |
| 5 技术设计 | 技术方案 |
| 6 代码生成 | 插件制作 |
| 7/8/9 校验 | 质量验证 |
| 10/11 打包安装 | 安装 |
| 12 试点 | 小规模试用 |
| 13 用户验收 | 验收 |
| 14 发布 | 正式交付 |
| 15 运营 | 使用与维护 |

### 8.4 失败时怎么展示

不要只说“失败了”。

要展示：

```text
当前阶段：试点验证
状态：未通过
原因：BOSS 推荐页 iframe 重载，无法稳定加载下一批
影响：只能稳定读取当前 16 条
建议：
  A. 改人工辅助翻页
  B. 申请官方 API/企业版导出
需要你决定：A 还是 B
```

### 8.5 验收也要可见

验收时给用户一张清单：

```text
请确认：
[ ] 你能用一句话开始任务
[ ] 你能看到进度
[ ] 你能停止任务
[ ] 你能拿到 Excel
[ ] 你全程没有看代码

全部确认后，插件才算正式交付。
```

```text
[ ] 5 技术方案与失败策略明确
[ ] 6 无密钥/无绝对路径
[ ] 7 静态校验通过
[ ] 8 自动测试通过
[ ] 8.1 目标一致性测试通过
[ ] 8.2 修复轮次不超过 3
[ ] 13 验收由真实用户确认，未自动代签
[ ] 9 沙箱权限通过
[ ] 10 zip + checksum
[ ] 11 安装 composed=true
[ ] 12 3/10/30 试点通过
[ ] 13 用户自然语言验收通过
[ ] 14 版本/说明/回滚齐全
[ ] 15 日志/监控可用

```

## 9. 反例：BOSS 插件

按本流程，BOSS 案例应：

- 节点 2 判定为黄色/红色（强风控）
- 节点 4 不允许把 `boss_start(...)` 交给用户
- 节点 12 在 3/10/30 条试点发现 iframe 重载
- 节点 13 用户验收不通过（用户看到代码）
- 节点 14 不发布“1000 条全自动”版本

结论：**不是插件工厂不能做，而是它必须在节点 2 就停止过度承诺。**
