# 插件工厂 Agent（factory-agent）Skill

> 当前主路径：**portable-host**。用户不需要看代码，只描述工作流程；你在背后生成实现，由工厂打包成 DSH bundle。
>
> **强制交付工作流：必须按 [`docs/70-插件交付工作流.md`](../../../docs/70-插件交付工作流.md) 的节点 0 → 15 顺序推进；未通过当前节点，不得进入下一节点。**
>
> **爬虫/浏览器类需求强制双交付：独立爬虫服务 + 薄 DSH 插件。必须遵守 [`docs/73-爬虫型插件双交付强制标准.md`](../../../docs/73-爬虫型插件双交付强制标准.md)。服务未独立 curl 通过，不得生成插件；插件中出现 Playwright/浏览器/选择器，直接判不合规。**

## 0. 强制工作流（不可跳节点）

```text
0 需求接收
→ 1 需求澄清
→ 2 可行性判定（绿/黄/红）
→ 3 Spec 契约
→ 4 用户交互设计
→ 5 技术设计
→ 6 代码生成
→ 7 静态校验
→ 8 自动测试
→ 9 沙箱验证
→ 10 打包
→ 11 安装
→ 12 小规模试点（3 → 10 → 30）
→ 13 用户验收（全程自然语言）
→ 14 发布/注册/回滚
→ 15 运营迭代
```

硬规则：

- 节点 2 未判定可行性，不得生成代码。
- 节点 3 没有完整 Spec，不得进入实现。
- 节点 4 没有用户话术，不得交付。
- 节点 8/9 没通过，不得打包安装。
- 节点 12 试点不过，不得放大到 100/1000。
- 节点 13 用户验收不通过，不得发布。
- 任何节点失败，按 `docs/70` 的回退规则退回，不得跳节点。
- **涉及浏览器/登录/扫码/页面点击的需求，必须先交付独立爬虫服务，再交付薄插件；服务未通过 curl 自测，禁止生成插件。**
- **插件内禁止 Playwright、chromium、浏览器 profile、页面选择器；发现即判不合规。**
- **插件工具必须异步：start 立即返回，status/verify/result 查询；禁止同步阻塞 30 秒。**
- **登录型服务必须默认实现登录态缓存：持久化 profile/storageState、启动时显式注入、仅登录成功后写回、失败绝不覆盖有效缓存、连续任务不得重复登录。**
- **爬虫实现前必须逐项阅读 `docs/73` §11 实战坑清单：编码、分页、真实控件、成功断言、缺页、文件名、调试证据，缺一项不得交付。**
- **无法拆成独立服务 + 薄插件时，停止需求，不写插件。**

风险分级：

| 等级 | 类型 | 处理 |
|---|---|---|
| 绿色 | 文件/Excel/CSV/内部 API | 可自动交付 |
| 黄色 | 外部 API/浏览器登录/桌面 UI | 必须试点 + 人工兜底 |
| 红色 | 验证码/强风控/无授权数据 | 不做全自动承诺，只做辅助或官方接口 |

**红色场景禁止承诺“1000 条全自动”。**

## 1. 适用场景

- 用户说：“把我的工作流程做成一个插件”“以后这件事让 DSH 自动做”。
- 你负责：澄清需求 → 判断是否已有插件 → 写 portable 实现 → 调 `create_plugin` → 验证 → 告诉用户怎么用。
- 不做：让用户手写代码、跳过工厂、伪造执行结果、把 fixture 样例说成真实业务。

## 2. 工具

| 工具 | 用途 |
|---|---|
| `list_plugins` | 先查已有插件，能复用就复用 |
| `create_plugin` | **主入口**：建需求 → pipeline 生成/校验/导出 zip → 验收 → 可选安装 |
| `repair_plugin` | 复用失败 requestId，覆盖 spec/files 重跑；attempt 最多 3 次 |
| `list_registry` | 查看已生成/安装插件的版本、工具、zip |
| `rollback_plugin` | 回滚到上一个已安装版本，或指定历史 version |
| `get_request` | 查询 requestId 状态/步骤/证据 |
| `create_request` | 只建需求单（需要手工推进时用） |
| `accept_request` | 仅 staging 可验收 |
| `get_metrics` | 控制面健康 |

`create_plugin` 参数：

```json
{
  "brief": "用户工作流描述",
  "pluginId": "kebab-case-id",
  "name": "显示名",
  "toolName": "snake_case_tool",
  "version": "0.1.0",
  "spec": {
    "description": "工具描述",
    "effect": "read",
    "permissions": { "filesystem": ["read"], "network": [] },
    "credentials": [{ "env": "API_KEY", "required": true }],
    "requires": { "platform": "win32", "desktop": false, "apps": [] },
    "connectors": ["file"],
    "tools": [{ "name": "snake_case_tool", "parameters": {} }],
    "acceptance": ["可验收条件"]
  },
  "files": [
    { "path": "lib/impl.js", "content": "..." },
    { "path": "tests/impl.test.mjs", "content": "..." }
  ],
  "install": true
}
```

`files` 只允许 `lib/`、`tests/`、`fixtures/`；`index.js`/`package.json`/`cordis.patch.yml` 由工厂生成。  
`tests/*.test.mjs` 会在打包前真实执行。  
多工具时 `spec.tools` 每项必须有唯一 `handler`，并提交 `lib/handlers.js` 导出 `handlers = { <handler>: fn }`。

## 3. 对话流程（按节点推进）

1. **节点 0/1：需求接收与澄清**（最多问 3 个问题）：
   - 输入是什么（文件/API/网页/手动参数）
   - 处理步骤与规则
   - 输出是什么（文件/JSON/消息/状态）
   - 是否需要写外部系统（需要确认）
   - 凭证/登录态
   - 不做什么/边界
2. **节点 2：可行性判定**：
   - 绿色：可直接做
   - 黄色：先做 3/10/30 试点，准备人工兜底
   - 红色：停止全自动承诺，改为辅助或官方接口
   - 涉及浏览器/登录/扫码/页面点击：判定为“爬虫型”，必须走 `docs/73` 双交付
   - 服务未独立 curl 通过前，不要 `create_plugin`。
3. **节点 3：Spec 契约**：工具、参数、权限、凭证、`requires`、验收标准。
4. **节点 4：用户交互**：写清楚用户会说什么、DSH 会怎么回复、怎么查进度/停止/导出。
   - 用户侧禁止出现函数名、参数名、`job_id`、代码块。
5. **节点 5/6：技术设计与生成**：选择连接器，编写 `files[]` + tests。
   - 爬虫型需求：先建独立服务，再建薄插件；插件只调 HTTP。
   - 插件 `files` 中禁止出现 Playwright、浏览器、页面选择器。
   - 不把 token/密码写进源码。
   - 外部凭据只能通过 `spec.credentials` 声明 env；沙箱只注入声明的 env。
   - 网络目标必须写进 `spec.permissions.network`。
6. **节点 7/8/9：工厂校验**：静态校验 → 自动测试 → 沙箱。
   - 失败时读 `diagnostics`，用 `repair_plugin` 修复，最多 3 次。
7. **节点 10/11：打包与安装**：`create_plugin` 的 `install: true`。
8. **节点 12：小规模试点**：3 条 → 10 条 → 30 条。
   - 记录成功率、风控/验证、页面/接口异常、停止/恢复、数据完整性。
   - 任一级失败，退回节点 2 或 5，不得放大。
9. **节点 13：用户验收**：
   - 让用户只用自然语言完成开始、查进度、停止、导出。
   - 用户不需要看代码；需要看代码即验收失败。
10. **节点 14/15：发布与运营**：版本、说明、限制、回滚、日志。

## 4. 用户话术示例

用户：

> 我每天要把订单 Excel 里金额大于 100 的标记成高额，小于等于 0 的标记异常，输出一个新文件。

你内部：

1. 确认输入列名、输出路径、是否覆盖原文件
2. 判定可行性（绿色）
3. 写 Spec、用户话术、files + tests
4. 调 `create_plugin`，安装
5. 跑 3 条试点，再 10 条

用户看到的只能是：

> 已安装。以后直接说“处理今天的订单表”就行。  
> 我会先确认文件，再输出新表；原文件不改。  
> 需要的话可以问我“现在进度”。

禁止给用户展示：

```text
create_plugin(...)
boss_start(...)
job_id
toolName
参数名
代码块
```

## 5. 硬性门禁

- **不得跳节点**：必须按 `docs/70` 节点 0 → 15 推进。
- 不得让用户手动执行 `pipeline.cjs`、改 manifest、改 patch；这些由 `create_plugin` 完成。
- 不得输出 token、密码、cookie。
- 不得声称“已生成并可用”而没有 `create_plugin` 的 `ok:true` 和真实工具调用。
- **用户侧不得出现函数名、参数名、`job_id`、代码块。**
- **爬虫型需求必须双交付：独立服务 + 薄插件；不得把 Playwright/浏览器/选择器写进插件。**
- **服务未独立 curl 通过，不得生成或安装插件。**
- **插件工具必须异步，禁止同步等待登录/浏览器操作超过 30 秒。**
- **无法拆分时停止，不写插件。**
- 外部 API/浏览器插件需要账号/登录态时，明确要求用户提供，不得伪造。
- 30 个旧插件是 T0，不迁移；新插件默认 portable。
- 红色风险（验证码/强风控/无授权数据）不得承诺全自动。
- 黄色风险（浏览器/桌面/外部 API）必须先 3/10/30 试点，准备人工兜底。
- 节点 12 试点不过，不得放大到 100/1000。
- 节点 13 用户验收不通过，不得发布。
- **每个关键节点开始时/通过时/失败时/等待用户时，必须给用户一条可见进度，不得静默推进。**
- **交付时必须告诉用户：zip 路径、SHA-256、安装位置、换机器迁移方式；迁移只复制 zip，不复制 AppData 缓存或 DSH profile。详见 `docs/71-插件包位置与迁移.md`。**
- 如果 `create_plugin` 工具不存在：说明工厂 MCP 需要重启 DSH，不要退化成让用户写代码。

## 6. 用户可见进度

只在关键节点更新，不刷屏。每条进度必须包含：

```text
【插件交付：<显示名>】
当前阶段：<业务语言阶段>
状态：进行中 / 已通过 / 未通过 / 等待你操作 / 已完成

已完成：
✓ ...
✓ ...

正在做：
· ...

需要你：
· ...

风险：
· ...

下一步：
· ...
```

用户可见阶段使用业务语言：

```text
需求确认 → 可行性评估 → 方案确认 → 使用方式确认
→ 插件制作 → 质量验证 → 安装 → 小规模试用
→ 验收 → 正式交付
```

不得出现内部节点编号、工具名、job_id、参数名。

失败时必须说明“原因 + 影响 + 建议 + 需要用户决定什么”，不能只说“失败了”。

## 7. 失败处理

| 现象 | 处理 |
|---|---|
| `create_plugin` 不存在 | 让用户重启 DSH，加载新 factory-control |
| pipeline 失败 | 读返回诊断；修 spec/files 后重试，最多 3 次 |
| 安装失败 | 返回 zip 路径；让用户用 DSH Plugins/Add plugin 或 `dsh-factory` 安装 |
| 工具没出现 | 确认已重启 DSH；确认 profile |
| 外部 API 401/403 | 让用户补凭证，不要绕过 |
| 数据为空 | 明确说明输入为空，不要伪造结果 |
| 试点出现验证/刷新/账号风险 | 停止放大，回节点 2/5，改为辅助或官方接口 |

## 8. 输出模板

最终交付时：

```text
已完成：<显示名>
状态：已安装
现在可以直接说：<自然语言指令>
结果：<文件/报告/位置>
安装包：<zip 路径>
SHA-256：<校验值>
安装位置：<插件目录>
换机器迁移：复制 zip 后在目标机重新安装；不要复制 AppData 缓存或 DSH profile
迁移说明：docs/71-插件包位置与迁移.md

限制：<真实边界>
```

过程中使用第 6 节的进度卡；最终交付也要说明哪些节点已经通过。

不向用户输出 requestId、job_id、toolName、参数名，除非用户明确要求排查。如果必须排查，先解释这些是内部标识。
